# Benchmark report — 2026-10-26, local VM (SQLite configuration)

## Environment

- Host: shared Muse VM, 8 GB RAM (memory-pressured during the run window),
  overlay disk; not a dedicated benchmark machine.
- Runtime: Python 3.12.3, uvicorn single process, gateway as shipped at this commit.
- Store: SQLite file with WAL + `synchronous=NORMAL` (the local/demo store).
  **PostgreSQL was not available on this VM**, so these numbers do not describe
  the Docker Compose / PostgreSQL configuration.
- Provider: deterministic mock (simulated latency 0 ms), so measured latency
  is gateway overhead + persistence, with no inference time.
- Client: Python `httpx` open-loop load generator, keep-alive connections
  properly pooled (200 max connections). An earlier closed-loop run with
  default client connection limits produced misleading client-side errors;
  that artefact is documented here so the numbers are not misread.

## Profile A — spec target profile (measured)

- Offered load: **25 requests/second for 60 seconds**, max 50 concurrent,
  `POST /v1/chat/completions`, non-streaming, 11-token prompt, dedicated
  project with rate limits raised so the limiter did not interfere.

| Metric | Result |
|---|---|
| Responses | 1500 |
| Success (HTTP 200) | 1500 (100%) |
| Client errors | 0 |
| p50 latency | 15.1 ms |
| p95 latency | 30.5 ms |
| p99 latency | 68.8 ms |

The spec §17.7 targets (25 rps, 50 concurrent, p95 gateway overhead < 150 ms)
were **met on this profile and environment**. The full 5-minute sustained
profile ships as `benchmarks/k6-gateway.js`; a 60-second measurement is what
was actually run here, and it is reported as such — not as a 5-minute result.

## Profile B — saturation probe (context, not a target)

Closed-loop, 50 concurrent workers, demo project defaults (600 rpm policy):

- The project rate limiter correctly capped successes at its 600 rpm policy;
  excess requests received `429 rate_limit_requests`.
- With correct client pooling there were no transport errors; request latency
  under saturation is dominated by the single-process event loop doing
  synchronous database work (a documented trade-off, see
  `docs/architecture/overview.md`).

## Limitations

- SQLite write serialisation and a single gateway process bound throughput;
  the PostgreSQL configuration with multiple workers is the intended
  production measurement environment and remains **unmeasured**.
- Numbers are local-VM measurements, reproducible with the scripts and
  profiles in `benchmarks/`; they are not a hosted-service SLA.
