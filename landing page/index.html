Where inference meets disciplined systems engineering.

Most LLM integrations fail quietly in production: runaway token budgets from concurrent race conditions, cascading outages from flaky remote endpoints, double-billed retries, and unmeasured model quality regressions.

ModelRail replaces naive provider wrappers with a hardened gateway architecture. Built as a modular monolith in Python 3.12 with PostgreSQL and Redis, it treats inference as an auditable, verifiable platform capability with zero cloud lock-in.

(03) — PLATFORM CAPABILITIES

Engineered for deterministic reliability, observable down to every token.

System Specification

Decouples client applications from upstream providers through configurable model aliases. Routes requests dynamically based on priority, cost per million tokens, or rolling latency percentiles across Mock, Ollama, and remote providers.

  • Priority Tiering & Fallback
  • Cost-Aware Token Routing
  • Rolling P95 Latency Routing
  • Deterministic Mock & Ollama

Solves the fundamental concurrency flaw in LLM gateways. Atomically reserves worst-case token costs prior to provider execution, preventing concurrent requests from over-allocating tenant budgets, and settles exact usage post-response.

  • Two-Phase Reserve & Settle
  • Multi-Tenant Org & Project Isolation
  • Sliding-Window RPM / TPM Limiters
  • Hard Budget & Concurrency Semaphores

Protects client services from upstream degradation. Automatically isolates failing providers with finite-state circuit breakers (Closed, Open, Half-Open), enforces per-provider timeouts, and retries with full exponential jitter without duplicate usage accounting.

  • Finite-State Circuit Breakers
  • Bounded Retries & Full Jitter
  • Independent Attempt vs Request IDs
  • Graceful Degradation & Failover

Ensures model quality is measured continuously rather than assumed. Evaluates models against categorized datasets (Reasoning, Extraction, Instruction, Refusal) with strict dev / held-out splits, blocking releases when accuracy degrades.

  • Dev vs Held-Out Benchmark Splits
  • Exact & Fuzzy Semantic Rubrics
  • CI Regression Gating (< 5% Threshold)
  • Historical Benchmark Run Tracking

						Technical FAQ
					


					

						

							
Ready to deploy a reliable AI gateway?

							Open Gateway Docs (/docs)
						


						

							

								
								

									

										ModelRail implements a strict two-phase reservation protocol. Before dispatching an inference request to an upstream provider, the gateway computes worst-case token spend based on policy limits and creates an atomic reservation in PostgreSQL/Redis. If remaining project budget cannot cover the reservation, the request is immediately rejected with HTTP 429 budget_exceeded. Once the provider completes, ModelRail settles exact token usage and releases the unspent reservation.
									

								

							

							

								
								

									

										Yes. ModelRail includes a built-in deterministic Mock Provider that responds instantly with configurable latency, streaming chunks, and simulated token generation, as well as an Ollama adapter for local open-source models (Llama 3.1, Mistral). The entire gateway, simulator, tests, and evaluation suite run offline on a local laptop without spending a cent.
									

								

							

							

								
								

									

										Logical requests and physical provider attempts are modeled as separate entities with distinct IDs (request_id vs attempt_id). When transient 5xx errors or timeouts trigger a retry or failover to another provider, each physical attempt is recorded with its own latency and status, but usage accounting and budget settlement are tied strictly to the final successful attempt of the parent request.
									

								

							

							

								
								

									

										ModelRail contains a standalone evaluation framework (packages/evals) with a versioned dataset (modelrail-eval-v1) divided into development and held-out test splits across Reasoning, Extraction, Instruction Following, and Refusal. The GitHub Actions CI pipeline runs the held-out evaluation suite automatically and asserts that pass rates do not degrade beyond the configured threshold (default 5%), blocking any release with regressions.
